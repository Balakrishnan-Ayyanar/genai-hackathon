# ClauseLens multi-source semantic layer

The active model is **`lightning.metastore.clauselens.sharing_model`**, versioned in this app as `clauselens-usl-1`. It is deployed and activated in the existing local Zetaris instance. No source data has been materialized into another database.

## Five separately registered fictional sources

| Fictional system | Editable file | REST endpoint | Zetaris raw table |
| --- | --- | --- | --- |
| Document registry | `data/sources/document-registry.json` | `/source/document-registry` | `CL_DOCUMENTS.registry` |
| Supplier registry | `data/sources/supplier-registry.json` | `/source/supplier-registry` | `CL_SUPPLIERS.registry` |
| Agreement register | `data/sources/agreement-register.json` | `/source/agreement-register` | `CL_AGREEMENTS.registry` |
| Approval register | `data/sources/approval-register.json` | `/source/approval-register` | `CL_APPROVALS.registry` |
| Policy repository | `data/sources/policy-repository.json` | `/source/policy-repository` | `CL_POLICIES.registry` |

These are independent files and registered connections with different native field names, served by one small local Node process. They simulate business systems; no real document-management or agreement product is connected. The application backend reads these files only when serving the source endpoints. Its evidence retrieval uses the Zetaris API and never calls a local-file fallback.

`data/evidence.json` and `scripts/register.sql` are retained legacy fixtures/registration for comparison. The old combined endpoint/view remains available, but no active evaluation query uses it. Editing only the legacy file will not update the active semantic sources.

## Semantic schema and actual mappings

Seven tables, queried beneath the model path above:

| Semantic table | Rows | Key mapping / relationship |
| --- | --- | --- |
| classification | 2 | `class_code` → `classification_id` |
| document | 2 | `report_code` → `document_id`; `classification_code` → FK `classification_id`; `owner_code` → `owner_id` |
| supplier | 2 | `vendor_code` → `supplier_id` |
| agreement | 2 | `contract_code` → `agreement_id`; `vendor_code` → FK `supplier_id` |
| agreement_purpose | 4 | one row per covered purpose; `contract_code` → FK `agreement_id` |
| approval | 5 | `report_ref` → FK `document_id`; `recipient_id` → FK `supplier_id`; `approver_ref` → `owner_id` |
| policy_clause | 4 | `clause_code` → `clause_id`; policy rule identifier and versioned configuration |

All seven tables have primary keys. Five foreign-key relationships are persisted in Zetaris DDL, not just drawn in the frontend. Dates are cast to USL DATE columns. Source IDs, passages, labels and versions are mapped explicitly. List-valued aliases and the small fixed policy configuration use JSON strings because the documented USL table schema accepts scalar types; agreement-purpose relationships are normalized into their own table. The USL graph is relational semantic metadata, not RDF/OWL reasoning.

## Model creation and activation

The checked-in generated files are the exact deployment inputs:

1. `scripts/semantic/01_sources_create.sql`: ten statements create five Lightning databases and register one REST table per source.
2. `scripts/semantic/02_model_create.sql`: creates the metastore/namespace, submits the seven-table COMPILE USL payload intact, and sets the model description.
3. `scripts/semantic/03_activate.sql`: seven activation queries bind source arrays and native field names to typed semantic columns.
4. `scripts/semantic/mapping.json`: readable model, source and column mapping manifest.

The definitions and the app's explicit select lists share `src/semantic.ts`. `src/sources.ts` validates and serves the independent source shapes. Source schemas are not generated by an LLM.

Deployment was performed using the supplied Zetaris `scripts/run_sql.py`, with `--dry-run` first. Do not blindly rerun the creation files: the model is already deployed, and repeat COMPILE behavior is not assumed. Keep the complete multi-table COMPILE statement intact. A future intentional model replacement must preserve the existing definition and re-activate all tables; the bundled guide notes replacement can clear activation.

To regenerate files for a deliberately changed model or source host:

```bash
CLAUSELENS_SOURCE_HOST=172.18.0.1 npm run semantic:generate
```

This only rewrites project SQL/JSON files; it does not change Zetaris. Verify the actual Docker bridge gateway and driver reachability before changing registered endpoints. Use the supplied runner's dry run and review the statements before deployment.

## Retrieval and decisions

Catalog loading retrieves all evidence through seven USL queries. Evaluation retrieves one case:

- Selected document, its classification and the selected supplier.
- All supplier agreements, including expired/future ones, and their purpose coverage.
- All approval records matching document, supplier and intended purpose, including opposing decisions. Owner and effective-date checks remain in the evaluator.
- All supplied policy clauses, which the evaluator filters by date and supported version.

The default case has eight relevant evidence records and three NDA-purpose helper rows. Zero matching approvals is an ordinary empty result, not an error and not proof an approval never happened. Tables are retrieved separately rather than through an inner join that could erase a document missing approval. Actual transport/invalid-source errors block evaluation without substituting legacy data.

Each evidence record contains `lineage` with its source system, semantic table and endpoint. Each new evaluation receipt contains seven SQL queries, row counts, semantic model identity/version and a normalized evidence hash. Open **Data connections**, **Source records**, the graph inspector or the evaluation receipt in the app to inspect these mappings.

The USL establishes common entity definitions and relationships. The fixed TypeScript evaluator still applies the fictional permission policy; foreign keys do not grant permission. Nightshift interpretation/explanation and H-MEM revalidation retain their existing roles. What-if facts remain copies in memory and never enter the source files or semantic tables.

## Verification and limits

`npm run verify:semantic` verifies the deployed model has seven tables and five foreign keys, compares all semantic counts to the actual REST sources, checks all 17 reconstructed evidence records against the legacy baseline, checks missing/conflicting approval retrieval, runs a cross-source join and briefly changes/restores a fictional approval label to prove live access without materialization. It saves `.runtime/semantic-verification.json`. A separate live check confirmed a healthy empty approval register returns zero rows. Source probes should run separately from browser tests.

The app validates query results and has a per-table 1,000-row retrieval ceiling; a result reaching that ceiling fails closed rather than silently truncating. Independent sources are read live and are not a cross-system transactional snapshot. Hashing records what was retrieved; it does not imply every source was read at one atomic instant. There is no production authentication, multi-user isolation or arbitrary policy extraction. This extension does not add a graph database or model-generated SQL/SPARQL.
